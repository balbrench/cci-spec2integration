---
description: [Manual] Compile the integration IR to a Logic Apps Standard solution (workflows, connections, Bicep, tests, CI/CD).
argument-hint: [spec-folder]
allowed-tools: Read, Edit, Write, Grep, Glob, Agent, Bash, PowerShell
---

Run the Azure pack's implementation chain.

Steps:
1. Resolve the integration folder (argument or most recently modified `specs/*/*/`).
2. Verify `.spec2integration/state.json` has `activePlatform: azure`; otherwise stop.
3. Verify `tasks.md` exists; otherwise instruct the user to run `/plan` and `/tasks`.
3a. **Lifecycle guard (highest-severity).** Apply `.claude/skills/lifecycle-guard/SKILL.md`: read `<folder>/status.json`, and if `lifecycle == post-implementation` or stage 10 (Implement) is `frozen`, STOP and print the redirect block. Re-running the implementation chain regenerates **every** platform artifact (`app/`, `adf/`, `sql/`, `infra/`, `connections.json`, `tests-mstest/`) from the IR — overwriting deployed, live-validated work. This is the single most destructive command on a frozen integration. Override only with `--force-regen` (prints the override warning). For targeted edits to a deployed solution, use `/change "<description>" <folder>`, which routes to the right Azure agent and edits only the named files.
4. Read `integration-ir.yaml` and resolve the run mode before invoking any compiler.
   - **Brownfield / migration mode**: `metadata.scenario == migration` and a top-level `source:` block is present.
   - **Greenfield mode**: `metadata.scenario == greenfield` (or omitted) and there is no top-level `source:` block.
   - If the IR mixes those signals, stop with a clear error. The Azure pack supports both modes, but only **one mode at a time** for a given `/implement-azure` invocation.
5. Run the `ir-validator` agent on the integration folder. If it returns any errors, stop and report them - do not proceed to compilation with an invalid IR.
6. Resolve the output directories. The integration folder mixes pipeline artifacts (spec, IR, contracts, reports) with the deployable Azure solution. To keep them separate, the Azure pack writes its output to **subfolders** of the integration folder, per `.claude/skills/logicapp-standard-layout/SKILL.md`.
   - **Logic Apps Standard project root** = `<integration-folder>/app/` - contains `host.json`, per-flow folders (NO `src/` wrapper), `connections.json`, `parameters.*.json`, `appsettings.*.json`, `local.settings.json`, `workflow-designtime/`, `Artifacts/Maps/`, `Artifacts/DataMapper/`, `Artifacts/Liquid/`, `Artifacts/Schemas/`, `lib/custom/net8/` (drop folder for sibling `Functions/` DLLs), `.vscode/`, `.funcignore`, `.gitignore`, `identity-role-assignments.json`, `global.json`, and the `.github/workflows/` folder.
   - **Sibling Functions project** = `<integration-folder>/Functions/` - a separate .NET 8 in-process WebJobs SDK project at the integration root (NOT inside the logic-app folder). Its csproj's `LogicAppFolderToPublish` resolves to `..\app` so DLLs land in `app/lib/custom/net8/` after `dotnet build`. This project holds in-process custom code (`InvokeFunction` targets) for Logic Apps Standard flows only - it is not the same as a stand-alone Function App.
   - **Stand-alone Function App projects** = `<integration-folder>/FunctionApps/<FlowName>/` - one .NET 8 isolated-worker project per IR flow whose `implementation.host == function-app`. Sibling to `app/` and to `Functions/`; deployed as separate Azure Function Apps. Emitted by `azure-functions-compiler`. Skipped when no flow routes to `function-app`.
   - **Data Factory artifacts** = `<integration-folder>/adf/` - pipelines, datasets, linked services, triggers, and optionally data flows for every IR flow whose `implementation.host == data-factory`. Sibling to `app/`, `Functions/`, and `FunctionApps/`; deployed via the factory module under `infra/`. Emitted by `azure-data-factory-compiler`. Skipped when no flow routes to `data-factory`.
   - **SQL schema** = `<integration-folder>/sql/` - `01-schema.sql` (tables: canonical staging, delivery-queue lifecycle, identity-map, validation-error, audit), `02-procedures.sql` (every stored procedure the workflows / Function Apps call), `03-grants.sql` (managed-identity DB users + least-privilege grants, tokenised `__mi_*__`), and `README.md`. Sibling to `app/` and `adf/`; Bicep provisions only the empty server + database, so this is the actual schema. Emitted by `azure-sql-schema-author`. Skipped when the IR has no `db` dependency.
   - **Bicep** = `<integration-folder>/infra/` - outside the logic-app folder so it is not bundled into the func deploy package; `azd` reads it from one level above.
   - **MSTest project** = `<integration-folder>/tests-mstest/` - separated from `app/tests/` (which is reserved for the designer's JSON request fixtures).
   - **azd manifest** = `<integration-folder>/azure.yaml` - at the integration folder root, with `infra.path: ./infra`. For Logic Apps Standard, do **not** add `services.logicapp.project: ./app`; `azd` provisions infra only, and the Logic App content under `app/` is package-deployed separately.
   - **Workspace file** = `<integration-folder>/<slug>.code-workspace` - opens `./app` in VS Code so the Azure Logic Apps Standard extension attaches to the deployable project; also include `./Functions` as a second folder entry if the integration has a sibling custom-code project, so developers can edit the C# source alongside the workflows.
   When invoking each agent below, pass the appropriate output directory explicitly. Do not let agents emit at the integration folder root except for `azure.yaml`, the `.code-workspace`, and `azure-review.md`.
7. Bucket every IR flow by `implementation.host` (default `logic-app-standard` when the field is absent). Then, in order, invoke:

   **Ordering is a hard dependency, not a suggestion — do NOT parallelize across a read-after-write seam.** The independent per-bucket compilers (`azure-logic-apps-compiler`, `azure-functions-compiler`, `azure-data-factory-compiler`) may run concurrently with each other, but the downstream agents consume their outputs and MUST run strictly after:
   - `azure-bicep-author` **MUST run after `azure-connections-binder` has finished writing `app/connections.json`** — it mirrors the exact `@appsetting('NAME')` names from `connections.json` into the Logic App site settings (step 6/4a of its agent). If bicep runs first (or in parallel) it reads a pre-binder/bare `connections.json`, invents its own app-setting names, and the deployed MI connections resolve to null endpoints (a deploy-blocking Critical the reviewer otherwise has to catch by manual cross-check).
   - `azure-workflow-tester` and `azure-cicd-author` MUST run after the artifacts they reference exist (`app/`, `tests-mstest/`, `adf/`).
   Treat the binder→bicep edge as serial every run.

   - `azure-logic-apps-compiler` (output `<integration-folder>/app/`) - runs for the `logic-app-standard` bucket. Emits `<FlowName>/workflow.json` per flow at the project root, `host.json`, `workflow-designtime/`, `Artifacts/Maps/<MapName>.xsl`, `Artifacts/DataMapper/<MapName>.lml`, `Artifacts/Liquid/<MapName>.liquid`, `Artifacts/Schemas/<SchemaName>.xsd`, `.funcignore`, `.gitignore`. **Skip this agent only if the `logic-app-standard` bucket is empty.**
   - `azure-functions-compiler` (output `<integration-folder>/FunctionApps/<FlowName>/` per flow) - runs for the `function-app` bucket. Emits one stand-alone .NET 8 isolated-worker project per flow (`<FlowName>.csproj`, `Program.cs`, `host.json`, `local.settings.json`, `Functions/<FlowName>Function.cs`, `Functions/Activities/`, `Functions/Orchestrators/` when `durablePattern` is set, `Models/`, `Mappings/`, `Helpers/`), plus its paired MSTest project `tests-mstest/<FlowName>.Tests/` (mapping conformance over the IR fixtures, behaviour, and log capture for anonymous endpoints). **Skip this agent only if the `function-app` bucket is empty.**
   - `azure-data-factory-compiler` (output `<integration-folder>/adf/`) - runs for the `data-factory` bucket. Emits `pipelines/<FlowName>.json`, `datasets/`, `linkedServices/`, `triggers/`, `dataflows/` (when transforms warrant Mapping Data Flow), `integrationRuntimes/` (when Self-Hosted IR is required), `factory/<factoryName>.json`, and `README.md`. **Skip this agent only if the `data-factory` bucket is empty.**
   - `azure-local-functions-author` (output `<integration-folder>/Functions/` - sibling project, NOT inside the logic-app folder, NOT the same as `FunctionApps/`) - scans the **Logic Apps Standard** workflows emitted above for `InvokeFunction` targets and emits `<ProjectName>.csproj` (TFM `net8`, in-proc WebJobs SDK), `<FunctionName>.cs` per target (instance class with `[Function]` from `Microsoft.Azure.Functions.Worker` + `[WorkflowActionTrigger]`), `Models/*.cs`, and `Helpers/*.cs`. The csproj's post-build target publishes DLLs to `<integration-folder>/app/lib/custom/net8/`. **Skip this agent only if step 1's scan finds zero `InvokeFunction` actions across all workflows.**
   - `azure-sql-schema-author` (output `<integration-folder>/sql/`) - runs when the IR has a `db` dependency (or a SQL-backed channel / a workflow that calls `executeStoredProcedure`). **MUST run after `azure-logic-apps-compiler` and `azure-data-factory-compiler`** — it greps the emitted `workflow.json` for the stored procedures the flows actually call and the `adf/dataflows` + `adf/datasets` for the sink table columns, then authors the tables, procedures, and MI grants those components assume exist. May run concurrently with `azure-connections-binder`. **Skip this agent only when the IR has no `db` dependency.**
   - `azure-dataverse-binder` (refines the emitted `adf/` and/or `app/` Dataverse artifacts in place) - runs **after** `azure-data-factory-compiler` / `azure-logic-apps-compiler` when the IR targets Dynamics 365 CE / Dataverse (a `dependencies[]` entry with `kind: rest` + `product: dataverse`, or an emitted `CommonDataServiceForApps` sink / Logic Apps Dataverse action). It binds the Dataverse-specific details the generic compiler cannot: the ADF linked service auth (no `tenantId`, user-assigned MI only), per-entity write method for the host (Copy activity is upsert-only; a Mapping Data Flow inserts by default and needs `alterRow` to update or upsert), per-host lookup binding (`@EntityReference` / `{lookup}@{alternateKey}` in ADF, Type fields in Logic Apps), alternate-key handling, null-overwrite and throttling settings, and the application-user / role-assignment snippet. Edits only the Dataverse fields; does not regenerate sibling artifacts. **Run it after `azure-connections-binder`** (it appends its application-user snippet to `identity-role-assignments.json`, which the connections binder creates; it never edits `connections.json`). May run concurrently with `azure-sql-schema-author`. **Skip this agent only when the IR has no Dataverse target.** See `.claude/skills/dataverse-365ce/SKILL.md`.
   - `azure-connections-binder` (output `<integration-folder>/app/`) - emits `connections.json`, `parameters.json`, `appsettings.dev.json`, `appsettings.prod.json`, `local.settings.json`, `identity-role-assignments.json`, `.vscode/`, `global.json`. Only runs when the `logic-app-standard` bucket is non-empty.
   - `azure-bicep-author` (output `<integration-folder>/infra/` for modules, `<integration-folder>/azure.yaml` for the azd manifest) - emits `infra/` modules and `azure.yaml`. The manifest's `services` block reflects only the buckets that `azd` deploys directly: one `services.<flowName>.project: ./FunctionApps/<FlowName>` entry per stand-alone Function App. Logic Apps Standard content under `app/` is provisioned via `infra/` and then package-deployed separately; Data Factory artifacts are wired in by the `dataFactory.bicep` module rather than as an azd service.
   - `azure-workflow-tester` (output `<integration-folder>/tests-mstest/`) - emits the MSTest project with `WorkspacePath` pointing at the relative path to `app/` from each test project. Only runs when the `logic-app-standard` bucket is non-empty.
   - `azure-cicd-author` (output `<integration-folder>/app/.github/workflows/`) - emits the GitHub Actions workflows. The pipeline includes one publish job per non-empty bucket (Logic App, each Function App, and the Data Factory artifact import).
   - `azure-reviewer` (output `<integration-folder>/azure-review.md`) - audits every emitted artifact tree.
   After the compilers run, also write `<integration-folder>/<slug>.code-workspace`. The `folders` array MUST contain `./app` (when present), `./Functions` (when present), and one entry per `./FunctionApps/<FlowName>` that was emitted. Without this, the C# / Function App projects are invisible in the VS Code Explorer.
8. After each agent, surface any TODOs or Bicep comment blocks it emitted.
**Gates 8a–8d (hard — run them; no generating agent has Bash, so none of them can parse, compile or test its own output).** After all step-7 agents have returned and before relying on the `azure-reviewer` verdict, run all four with one command:

    powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-azure-artifacts.ps1 -Folder <integration-folder> -Build -Test -ReportFile <integration-folder>/implement-gates.json

(`pwsh` on Linux/macOS.) Each `ERROR` line names the rule and the file. Route it back to the agent that owns the file, with the exact message, then re-run the command. Repeat until it exits 0. The **last** run must be the full command above, so that `implement-gates.json` records the final result: `scripts/refresh-status.ps1` reads that file for stages 10 and 11. A gate that could not run (no `az`, no `dotnet`) is recorded as `not-run` and leaves stage 10 `blocked`; never report it as passed.

8a. **Bicep compile** (`-Build`): `az bicep build --file infra/main.bicep --stdout`, so no transient `main.json` is left behind. A failure (`Error BCP...`) means every deployment path is broken; send it to `azure-bicep-author` with the file:line and BCP code. (This gate exists because a space-separated `@allowed([ 'A' 'B' ])` / `BCP236` shipped undetected before it was added.) Also confirm `azure-bicep-author` emitted `infra/main.parameters.json` (azd reads it, not `.bicepparam`); if it is missing, bounce it back, because `azd provision` otherwise hangs on the no-default params.
8b. **ADF JSON validity** (always): every `adf/**/*.json` must strict-parse. Send a failure to `azure-data-factory-compiler` with the file, line/column and parser message. (This gate exists because an extra `}` from closing a Web-activity `body` and `typeProperties` inline as `} }` shipped invalid pipeline JSON undetected until `az datafactory` import.)
8c. **Static artifact rules** (always). The script strict-parses every `app/` and Function App `host.json` JSON file and enforces the rules the runtime applies but the agents cannot test:
    - no `limit` on `ServiceProvider` actions;
    - no `pattern` / `patternProperties` in a Parse JSON schema;
    - no `trackedProperties` on a secured action or trigger;
    - no `SecureString` / `SecureObject` in `parameters.json`;
    - no `FROM EXTERNAL PROVIDER` in `sql/`;
    - every `storedProcedureName` a workflow calls is created in `sql/`, with every `storedProcedureParameters` key declared as a procedure parameter;
    - every Function App has its paired `tests-mstest/<FlowName>.Tests/` project.
    It also warns on one-case `Switch` actions, SQL audit groups that record statement text, and test projects missing the MSTest `Using`. Route errors to the owner: workflows → `azure-logic-apps-compiler`, `parameters.json` → `azure-connections-binder`, `sql/` → `azure-sql-schema-author`, `infra/` → `azure-bicep-author`, Function Apps and their tests → `azure-functions-compiler`. Decide each `WARN` from the IR (for example the audit-group warning is a Sev-1 when a SQL-bound message is `confidential` / `restricted` or has `pii` fields) and record any accepted one in `decisions.md`.
8d. **.NET build and test** (`-Build -Test`, when any `.csproj` was emitted). The script builds `Functions/` first (its post-build step publishes into `app/lib/custom/net8/`, which the workflow tests load), then every Function App and test project. It then runs `dotnet test` on each `tests-mstest/*/*.Tests.csproj` **one at a time**. Never run the test projects in parallel or through a solution-level `dotnet test`: every Logic Apps test host binds port 7071. A build failure goes back to the agent that owns the project, with the compiler error. A test failure goes to the owner of the code under test, or to `azure-workflow-tester` when the test itself is wrong; read the SDK limits in `logic-apps-standard-testing` first (callback mocks, `Switch` branches, custom `Terminate` codes). The pass/fail counts are in `implement-gates.json` for the step-12 summary.
9. If the `azure-reviewer` verdict is `BLOCKED`, stop and print all Critical findings. Do not proceed further - the solution must not be considered complete while Critical findings exist.
10. **Only when the source IR is reverse-engineered** (`<integration-folder>/integration-ir.yaml` has a top-level `source:` block, typically `source.platform: biztalk`), call the `secret-scanner` agent with the full list of directories written by agents in step 7: `<integration-folder>/app/` (when present), `<integration-folder>/Functions/` (when present), `<integration-folder>/FunctionApps/` (when present - scans every `FunctionApps/<FlowName>/` project), `<integration-folder>/adf/` (when present - scans pipelines, datasets, linked services, triggers), `<integration-folder>/sql/` (when present - scans the schema/procedure/grant scripts), `<integration-folder>/infra/`, `<integration-folder>/tests-mstest/` (when present), plus the top-level files `<integration-folder>/azure.yaml` and `<integration-folder>/<slug>.code-workspace`. If it returns `BLOCKED`, print its Sev-1 findings. Skip this step for greenfield: the `azure-connections-binder` and `azure-bicep-author` agents emit only managed-identity and Key Vault references by design, and the `azure-reviewer` audit in step 7 already enforces that no inline secrets appear in the generated artifacts.
11. Compute SHA-256 hashes of every file written by the agents in step 7 (across every emitted bucket - `app/`, `Functions/`, `FunctionApps/<FlowName>/`, `adf/`, `sql/`, `infra/`, `tests-mstest/`, plus the top-level `azure.yaml` and `.code-workspace`). On Windows use PowerShell `Get-FileHash -Algorithm SHA256`; on Linux/macOS use `sha256sum`. Do not hash `implement-gates.json` or other reports. Store the baseline in the **per-integration** `<integration-folder>/status.json` (not in the global `.spec2integration/state.json`); these are preserved keys the status script cannot derive (see the `pipeline-status` skill). Read the existing `status.json`, add or replace only the top-level keys `artifactHashes` (flat object mapping repo-relative file path to hex digest) and `lastImplement` (`{ "completedAt": "<ISO-8601>", "flowCount": N, "host": "<logic-app-standard|function-app|data-factory>", "verdict": "<PASS|BLOCKED>", "artifactCount": N }`), then write it back preserving all other keys. This baseline is read by `/drift-check`.
12. Final step: print the Azure Reviewer verdict and counts, the secret-scan verdict (or `skipped (greenfield)` when step 10 was skipped), the per-bucket flow counts (`<L> logic-app-standard / <F> function-app / <D> data-factory`), and a local development quick-start:
    ```
    To run locally:
    1. Open <integration-folder>/<slug>.code-workspace in VS Code (or just open <integration-folder>/app/ as a folder).
    2. Start Azurite: Ctrl+Shift+P -> "Azurite: Start"
    3. Press F5 (or run: `cd app && func host start`)
    4. Logic App available at http://localhost:7071
    5. For stand-alone Function Apps: `cd FunctionApps/<FlowName> && func start`
    6. For Data Factory artifacts: deploy via `azd up` - there is no local ADF runtime.
    ```
13. Rebuild `<integration-folder>/status.json`: run `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/refresh-status.ps1 -Folder <integration-folder> -RefreshedBy /implement-azure`. Do not write stage rows yourself. The script derives stage 10 from the artifact tree, the `azure-review.md` verdict and `implement-gates.json`, and stage 11 from the test results; it keeps the `artifactHashes` / `lastImplement` baseline written in step 11.
14. Read the refreshed `<integration-folder>/status.json` and ask one short follow-up question in chat: `What do you want to do next?`
   - If the chat surface supports selectable options, offer them as choices.
   - Otherwise render a numbered list and wait for the user's reply.
   - Print `Why: <next.reason>` before the choices.
   - Offer these choices:
     - `Run recommended step: <next.command>`
     - `Fix azure-review.md or secret-scan findings, then re-run /implement-azure <integration-folder>`
     - `Stop here`
